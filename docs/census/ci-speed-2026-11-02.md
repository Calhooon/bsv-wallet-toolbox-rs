## The design

**The cache.** `Swatinem/rust-cache` v2.9.3 (`d1527c8f67ef9af357290475d4af4b0fab8f12e0`) replaces `actions/cache` in the Test Suite, Clippy, vectors, fixtures and Documentation jobs. Its key is the rustc release and host of every installed toolchain, a hash of the `CARGO*` and `RUST*` environment (so `RUSTFLAGS=-Dwarnings`, `CARGO_PROFILE_DEV_DEBUG` and `CARGO_INCREMENTAL` are in it), a hash of every `Cargo.lock` and `Cargo.toml`, and the job's `shared-key`. `Cargo.lock` is not tracked (a library), so each job resolves it before the cache step (`test -f Cargo.lock || cargo generate-lockfile`, the fixtures job's existing form) and the key hashes the lock the build uses, not the manifest alone; a new upstream release moves the lock hash, and the action restores from the same prefix without it, so only the changed crates rebuild. The action caches the dependencies' build alone: the workspace crate, incremental artifacts and anything a week stale are pruned before the save.

| job | shared-key | builds |
|---|---|---|
| Test Suite (ubuntu-latest, stable) | `test-sqlite-remote` | `--lib` with `sqlite,remote`, `--test '*'` and `--doc` with `sqlite,remote,bench-support` |
| Test Suite (remote only) | `test-remote` | `--lib --tests` with `remote` alone |
| vectors, fixtures | `test-sqlite` | test builds with `sqlite` (the default set): one cache, saved by whichever job ends sooner |
| Clippy | `clippy` | check builds, `--all-targets` with `sqlite,remote` and `remote` alone |
| Documentation | `docs` | `cargo doc --features sqlite` |

Clippy and Documentation keep their own keys: their builds are check and rustdoc artifacts, which a test build cannot reuse. A cache is saved by a push to `main` or `beta` alone (`save-if: github.event_name == 'push' && !startsWith(github.ref, 'refs/tags/')`): a PR's cache belongs to its own ref and no other PR can restore it, while a line's cache is restored by every PR into that line, and per-PR saves would evict the line's caches under the 10 GB limit. semver and ratchet keep `actions/cache` for this round (named in the next cut).

**The profile.** `CARGO_PROFILE_DEV_DEBUG=0` and `CARGO_INCREMENTAL=0` in the workflow env, not a `[profile.ci]`: every cargo call inherits the env, including the `cargo test ... -- --list` calls of `tools/arch-doc-tests.sh`, which a `--profile ci` would not reach (the script builds the default profile, so a CI profile would rebuild the whole tree for it), and `Cargo.toml` is outside this lane. The `test` profile inherits `dev`, so the test builds lose `-C debuginfo=2`: on a scratch crate, `cargo test --no-run -v` shows `debuginfo=2` twice without the env and no `debuginfo` flag with it.

**The linker.** lld, the toolchain's own: on `x86_64-unknown-linux-gnu`, stable Rust links with its bundled `rust-lld` by default since 1.90 [D] (the Rust 1.90 release notes), so the linker cut is already in and `RUSTFLAGS` names no linker. On 1.98.1 `-C linker-features=+lld` is refused on stable ("is unstable, and also requires the `-Z unstable-options` flag") and only `-C link-self-contained=-linker` is stable [X], so lld cannot be named in `RUSTFLAGS` on stable; mold would need an install action in every linking job and a `-C linker-features=-lld -C link-arg=-fuse-ld=mold` pair, for a link that is a small share of a build without debuginfo. A step after the build prints the `.comment` mark the linker left in the unit-test binary (`readelf -p .comment`), so the PR's run shows which linker it used.

**nextest.** `cargo-nextest` 0.9.146 through `taiki-e/install-action` v2.87.26 (`f7e5d7c961414b23f5b25b2da9294395d08513ad`, the pin the semver job already uses; 0.9.146 is the newest nextest that pin's manifest names), with `--no-fail-fast` so a red run names every failure. Each feature set builds with `cargo test --no-run` as its own step, then runs under `cargo nextest run`, which lists from that build and compiles nothing (locally `Finished ... in 0.19s` before each run [X]). Doc tests stay on `cargo test --doc` (nextest does not run them), with the integration step's feature set (#253). nextest runs every test in its own process; the statics the suite holds (`FREE_MOCK_SERVERS`, the pace gates, the lookup fixture's subjects, two regexes) are per-process pools and caches, none a resource another process could contend for.

**The two jobs.** The Test Suite keeps its name and matrix, so the required context `Test Suite (ubuntu-latest, stable)` is unchanged: the `sqlite,remote` unit build and run, the `sqlite,remote,bench-support` integration build and run, the architecture doc tests (`ARCH_DOC_LIB_FEATURES=sqlite,remote`, `ARCH_DOC_TEST_FEATURES=sqlite,remote,bench-support`, listing from the two builds beside them) and the doc tests. The remote-only build and run (#429) is the new job `Test Suite (remote only)`, which runs at the same time; the captain adds its context to beta's protection at the landing (the workflow header names eleven contexts).

**The shard decision: no shard.** The longer job's cached build is well under eight minutes by the measurement below, and sharding cannot cut a job below its build: each shard rebuilds (or downloads) the same binaries, and the part a partition divides is the run, 27 seconds of the job locally. A shard would also take another queue slot per run (below). If the PR's run shows the Test Suite above eight minutes, the shard is `--partition count:k/n` over the integration targets, with the union check this round ran as its witness.

**The twin `pull_request` run.** `on.pull_request.types` drops `labeled` and `unlabeled` and is now `[opened, synchronize, reopened]`. `gh pr create --label` fired `opened` and `labeled` within a second: two runs in one concurrency group, one cancelled, and GitHub read the cancelled run's check-runs as the latest per name, so the merge stayed BLOCKED until the cancelled run was re-run (PRs #595, #608 and #610: three 45-minute waits). The semver job read the label from the event payload, which is why the trigger had those types. It now reads the label live: `gh pr view "$PR_NUMBER" --json labels --jq '[.labels[].name] | index("api-break") != null'` under `GITHUB_TOKEN`, with the job's existing `pull-requests: read` (no write permission, no secret), captured before use so a refused read stops the step under `set -e` rather than reading as no label. Everything after the read is unchanged: `API_BREAK` starts `false`, the PR path sets it from the read, the push path's merged-PR search sets it as before, and only `API_BREAK=true` with a reported break turns a failure into the owner-approved notice. A label added later reaches semver through a plain re-run of the job: the re-run replays the old payload, but the payload now supplies only the PR number, and the label is read from the API at that moment. The query read against live PRs: PR #610 `false`, PR #592 (merged with `api-break`) `true` [X]. `tools/workflow-grants-check.sh` still passes, so release.yml's reusable call grants every job's permissions.

After: `ci-${{ github.event_name }}-${{ github.event.merge_group.head_ref || github.event.pull_request.number || github.ref }}`, `cancel-in-progress` unchanged (never on a tag). A tag's call into ci.yml keys `ci-push-refs/tags/<tag>`, still never cancelled.

### semver under merge_group: judged on the group, with its PR's label

The choice: semver runs its full check on `merge_group` rather than reporting success on the PR's word. A group's head ref names the PR it was built for, `refs/heads/gh-readonly-queue/beta/pr-<n>-<parent sha>` [X] (the CLI's queue runs read 2026-11-03: `gh-readonly-queue/beta/pr-468-d21a1964...`, `pr-470-6a5d9dc3...`, `pr-467-c7d90676...`, `pr-466-05cf35d4...`; each name's sha is the parent, and each group's head sha is the next group's parent: the queue builds each PR's group on the group ahead of it). So the step reads the number between `pr-` and the next `-` (refused unless it is digits), reads that PR's `api-break` label live as the PR path does, and takes the group's parent commit (`merge_group.base_sha`, fetched, refused when unfetchable) as the baseline: the diff the check reads is that PR's own commits as the queue will land them, rebased onto beta and every group ahead, and the label that permits a break is that PR's own. The release type reads the baseline's `Cargo.toml` as the PR path does. Why not the success-on-merge_group form: a PR's own run judged it against beta's tip when it ran, and a break the rebase brings in (a PR ahead in the queue changing a type this PR's code exposes) would land unjudged until the push run, which gates nothing; the full check costs one semver job (2:48 warm in #626's run) per group. The `pull_request` and `push` paths are unchanged; the job's grant stays `contents: read, pull-requests: read`, and `tools/workflow-grants-check.sh` reads `workflow grants: ok`.
